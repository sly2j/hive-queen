# Research: hive queen 2.0, other agent systems, multi-node, done signals, resume

Date: 2026-10-27. Scope: what hive needs to know to add a driver abstraction so Claude Code,
OpenAI Codex CLI, OpenCode and pi can run as workers and as the queen; generic tmux idle
heuristics; and running a queen-less hive on another node driven over ssh (host `swarm`).
Out of scope: designing the abstraction (that is `planner`'s), and any state-changing hive or tmux
command. Every web source was accessed 2026-10-27. "V" marks a fact verified in the cited
docs, in local `--help`, or by a live read-only command. "I" marks an inference, and
"unverified" marks a claim that is from memory or from a third party only.

## Executive summary

- **Claude Code ships as the reference driver.** It is the only one with per-session remote control
  reachable from claude.ai and the phone. It also has per-pane hooks via `--settings` and resume by
  name. Caveat (V): it needs claude.ai subscription login, not an API key or OAuth token.
- **OpenCode is a ship candidate with a different shape.** It runs one server with many sessions,
  plus a browser UI (`serve`/`web`, `attach`, v2 `pair`). Remote devices need ssh forwarding or
  `pair --remote`. Settle v1 (1.19.4) vs v2 (2.0.14) first.
- **Codex is roadmap for remote and viable as a worker now.** `remote-control` is experimental, and
  its pairing is documented only via the macOS/Windows desktop app. Stop and PreToolUse hooks, `-c`
  overrides and `resume <name>` make it a viable tmux worker.
- **pi is roadmap for remote (none official).** It has the cleanest primitives: `-n` and
  `--session-id` at launch, `-e` extensions, a blocking `tool_call`, and an `agent_settled` event.
- **Done/idle signal**: every agent has a native turn-finished event (A3). Inject a per-pane hook
  that writes a status file, and fall back to a tmux `capture-pane` hash.
- **Multi-node**: `ssh -o BatchMode=yes swarm 'hive list'` works today (V, section C).

## Claude Code

Local `claude --version`: 2.1.311 (V).

**A1 Remote Control** (V, https://code.claude.com/docs/en/remote-control):
- Flags: `claude --remote-control [name]` (alias `--rc`). In-session `/remote-control [name]`.
  `--remote-control-session-name-prefix` appears in `--help`.
- Server mode is a separate subcommand: `claude remote-control` with `--name`, `--spawn`,
  `--capacity`, `--permission-mode`, `-c`, `--session-id`. It refuses a global `--settings`, so
  hive should keep using interactive `--remote-control`.
- Naming precedence: a name passed via `--name`/`--remote-control`/`/remote-control`, then
  `/rename`, then the last message, then auto `<hostname>-<adjective>-<noun>`. A rename on
  claude.ai syncs back.
- The user connects at claude.ai/code or in the Claude app's Code tab (computer icon, green dot).
- Requirements: a Pro/Max/Team/Enterprise claude.ai login. API keys, `apiKeyHelper`,
  `setup-token`/`CLAUDE_CODE_OAUTH_TOKEN`, Bedrock/Vertex/Foundry, a custom `ANTHROPIC_BASE_URL`
  and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` all prevent it. An ineligible session still
  starts, with a failure notice.
- Limits: one RC session per process. `remoteControlAtStartup: true` only works from user or
  managed settings.
- Unverified: whether a first `--remote-control` in a fresh config dir shows an "Enable Remote
  Control?" consent prompt that would block a pane.

**A2 Identity and resume** (V, https://code.claude.com/docs/en/sessions, `--help`):
- Transcript path: `<config_dir>/projects/<cwd, non-alphanumerics to '-'>/<uuid>.jsonl`, with
  30-day retention (`cleanupPeriodDays`). `CLAUDE_CODE_PROJECT_DIR_NAME` (v2.1.234+) pins the
  directory name, and only when `CLAUDE_CONFIG_DIR` is set.
- `--session-id <uuid>` chooses the id at launch, so hive can assign ids deterministically.
- `--resume <id|name|path>`, `--continue`, `--fork-session`. A resume by an exact name works. An
  ambiguous name opens a picker, which would hang a headless pane.
- Resume restores the permission mode (plan included; `bypassPermissions` needs its flag again).
  It does not restore
  `--settings`, `--mcp-config`, `--plugin-dir` or `--add-dir`, so hive must pass them again.
- Resume reconnects RC recorded in the conversation. If another live process still holds RC for
  that conversation, the second prints "Remote Control not started here".
- I: relaunching with `--resume <id> --remote-control <name>` should give a working RC session.
  Test whether it reattaches or registers a new one.

**A3 Done signal** (V, https://code.claude.com/docs/en/hooks, /settings, /statusline):
- Common hook input: `session_id`, `transcript_path`, `cwd`, `permission_mode`,
  `hook_event_name`.
- `Stop` fires when the main agent finishes a turn (not on user interrupt; API errors fire
  `StopFailure`). It adds `last_assistant_message`, `background_tasks` and `session_crons`;
  empty arrays mean truly done.
- `Notification`, with `notification_type`:
  - `permission_prompt`: fires about 6 s after the prompt appears, so this is the blocked signal.
  - `idle_prompt`: fires about 60 s idle.
  - Also `agent_needs_input` and others.
- `SessionStart` carries `source` (`startup|resume|...`) and `session_title`. `SessionEnd`
  carries `reason`.
- Injection: `--settings <file-or-json>` sits above user, project and local settings and below
  managed. Hook arrays merge across sources, so per-pane hooks need no user-config edit.
  `--setting-sources` restricts which files load.

**A4 Unattended** (V, https://code.claude.com/docs/en/permission-modes, /permissions):
- Modes: `default`/`manual`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`.
- `auto` is classifier-reviewed. It drops broad allow rules such as `Bash(*)`, needs a supported
  model, and pauses after 3 consecutive or 20 total blocks (a stall risk unattended).
- `dontAsk` denies anything that would prompt, but PreToolUse allow still works.
- `bypassPermissions` shows a one-time warning dialog.
- The trust dialog appears only in interactive mode. hive's memory fact (verified 2026-10-22) says
  trust is `projects[<git toplevel>].hasTrustDialogAccepted` in `<config_dir>/.claude.json`; the docs
  only say `~/.claude.json`.
- `CLAUDE_CONFIG_DIR` moves settings, transcripts and plugins. The docs recommend one dir per
  account. Each dir needs its own claude.ai login for RC.
- Gap: the docs do not list first-run onboarding dialogs (theme, login) for a fresh config dir.

**A5 Queen** (V, https://code.claude.com/docs/en/memory, /hooks):
- CLAUDE.md files concatenate from root to cwd. `CLAUDE.local.md` is appended.
- `AGENTS.md` is read only when no CLAUDE.md exists (v2.1.277+). Otherwise use `@AGENTS.md`.
- An external `@import` in a project file triggers a one-time approval dialog, which would block a
  fresh pane.
- PreToolUse: exit 2 blocks. JSON `permissionDecision` takes `allow|deny|ask|defer`. With
  `"onFailure": "block"` (v2.1.295+) a hook error fails closed. The current guard.py relies on all
  of this, and it still matches the docs.

**A6** (V, https://code.claude.com/docs/en/setup): install via
`curl -fsSL https://claude.ai/install.sh | bash` (to `~/.local/bin/claude`), npm
`@anthropic-ai/claude-code`, or apt/dnf/apk repos. Linux x64/arm64. Proprietary license
(https://raw.githubusercontent.com/anthropics/claude-code/main/LICENSE.md).

## OpenAI Codex CLI

Local `codex-cli 0.164.0` (V, which matches npm latest).

**A1 Remote** (V, local `--help`; https://learn.chatgpt.com/docs/developer-commands?surface=cli,
https://learn.chatgpt.com/docs/remote-connections.md):
- `codex remote-control [start|stop|pair] [--json] [--no-daemon]` is marked "[experimental]". It
  runs an app-server daemon with remote control. `pair` prints a short-lived code; its JSON has
  `pairingCode`, `environmentId` and `expiresAt`.
- The docs say phone pairing is set up in the desktop app ("you can't set it up from the Codex
  CLI"), and they list macOS and Windows hosts, not Linux.
- A third-party post claims CLI-only pairing via
  `codex app-server --remote-control --listen off`, tested on Windows 0.147.0
  (https://roboin.io/article/en/2026/08/19/enable-remote-control-using-codex-cli/). Unverified.
- Local, multi-client: `codex app-server --listen ws://|unix://`. A TUI can attach with
  `codex --remote <url>`. `codex agents` browses sessions on the shared daemon, and
  `codex queue --thread <id|name> --message TEXT` injects a message into a session.
- I: `queue` gives the queen a way to message a worker without `send-keys`.

**A2 Identity and resume** (V, `--help` and docs):
- `codex resume [ID|NAME] [PROMPT]`, `--last` (cwd-scoped unless `--all`), `codex fork`,
  `codex exec resume`.
- Names are set in-session with `/rename` or `/new <name>`. There is no `--name` at launch (V,
  `--help`).
- Rollouts live under `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`. The directory exists
  locally; the filename pattern is unverified in current docs.

**A3 Done signal** (V, https://learn.chatgpt.com/docs/hooks,
https://learn.chatgpt.com/docs/config-file/config-reference.md):
- Hook events: `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`,
  `PostToolUse`, `Stop`, `Interrupt`, `SubagentStart`/`Stop`, `Pre`/`PostCompact`. The stdin JSON
  carries `session_id`, `transcript_path` and `cwd`.
- `notify = [cmd...]` gets a JSON argument with `type: "agent-turn-complete"` (payload fields are
  unverified in official docs). It is user-level only; project config cannot set it.
- `-c key=value` overrides work on every subcommand (V), so per-pane
  `-c 'notify=["/path/hook"]'` is plausible (I, test it).
- Hook trust: new or changed hooks are skipped until trusted via `/hooks`, or bypassed with
  `--dangerously-bypass-hook-trust`. That is a real friction point for hive-injected hooks.

**A4 Unattended** (V, `--help`, config-reference):
- `-a on-request|never`, `-s read-only|workspace-write|danger-full-access`, `--approve-for-me`,
  `--yolo`. `--full-auto` is absent from the 0.164 help.
- Project trust is `[projects."<path>"] trust_level`. The fresh-pane prompt is not documented
  (unverified). I: pre-empt it with `-c 'projects."/p".trust_level="trusted"'`.
- Other dialogs can be suppressed with `notice.hide_*` and `check_for_update_on_startup=false`.
- `CODEX_HOME` is the config dir; auth lives in `auth.json` per home when
  `cli_auth_credentials_store=file` (I that this isolates homes).

**A5 Queen** (V, https://learn.chatgpt.com/docs/agent-configuration/agents-md.md, /hooks,
/agent-configuration/rules.md):
- AGENTS.md is read globally (`$CODEX_HOME/AGENTS.override.md` or `AGENTS.md`), then one file
  per directory from root to cwd, concatenated, up to 32 KiB.
- PreToolUse can deny (exit 2 or `permissionDecision: deny`), but `ask` is unsupported. guard.py's
  "ask" paths (spawn `--env`, `--trust`, `down`) therefore have no direct equivalent. A Codex
  queen would have to deny them, or route through `PermissionRequest` (I). Coverage gaps (V,
  https://learn.chatgpt.com/docs/hooks#tool-coverage): hooks do not cover hosted tools, and
  `write_stdin` does not rerun PreToolUse. Equivalent queen enforcement is therefore
  unverified.
- `.rules` Starlark `prefix_rule(pattern, decision=allow|prompt|forbidden)` provides an
  allowlist layer. The read-only sandbox plus a PATH wrapper is a fallback (unverified).

**A6**: npm `@openai/codex`, `brew install --cask codex`, or
`curl -fsSL https://chatgpt.com/codex/install.sh | sh`. Linux x86_64/arm64 musl binaries.
Apache-2.0 (https://github.com/openai/codex). Not installed on swarm (V).

## OpenCode

Identity (V): github.com/anomalyco/opencode (formerly sst/opencode), MIT. The Go
`opencode-ai/opencode` is archived and became Crush, so it is not this one. **Two live
generations:**
- v1.19.4: latest GitHub release, 2026-10-22, docs at https://opencode.ai/docs/.
- v2.0.14: the local binary at `~/.opencode/bin/opencode`, docs at https://opencode.ai/v2/docs/.
  It changes the CLI, the permission schema and the config precedence.

OpenCode is installed on swarm at `~/.local/bin/opencode` (plus `opencode2`). Which generation it
is was not checked.

**A1 Remote** (V, https://opencode.ai/docs/server/, /docs/web/, https://opencode.ai/v2/docs/cli):
- v1: `opencode serve --port 4096 --hostname 127.0.0.1 [--mdns] [--cors]` and `opencode web`.
  Auth is HTTP basic via `OPENCODE_SERVER_PASSWORD`; without it the server is open.
- The TUI is itself a client of an internal server. `opencode attach <url>` connects another TUI,
  and the docs say an attached TUI shares "the same sessions and state" with web.
- v2: a shared background `opencode service` (`start|stop|status|set`) owns sessions unless
  `--standalone` is passed. `opencode pair` prints a single-use link plus QR code, valid 5 min,
  for web access. `--server <url>` points a client at a server. The `pair` link is localhost by
  default. Another device needs ssh forwarding or `pair --remote`, and the first remote exposure
  asks for confirmation (`--yes` without a terminal) (V, https://opencode.ai/v2/docs/cli/web).
- No official phone app was found. The web UI is the phone path.
- Unverified: a TUI and a browser driving one session concurrently. There is no per-pane
  "remote name" either: one server or pairing covers many sessions, and v1 sets a title via
  `POST /session {title}`.

**A2 Identity and resume** (V, https://opencode.ai/docs/cli/, local v2 `--help`):
- `--continue/-c`, `--session/-s <id>`, and `--fork`.
- `opencode run --title`. The TUI has no `--title`, so a name is set through the API (PATCH
  `/session/:id`).
- v2 storage is SQLite at `~/.local/share/opencode/opencode.db` (`OPENCODE_DB` overrides it;
  `opencode debug paths`).

**A3 Done signal** (V v1, https://opencode.ai/docs/plugins/, /docs/server/, /docs/config/):
- Plugin events: `session.idle`, `session.status`, `session.error`, `permission.asked`, and
  `tool.execute.before`/`after`.
- External access: SSE `GET /event` and `GET /session/status` for all sessions, which is the best
  "is it done" API of the four, with no hook injection needed.
- Per-process config: `OPENCODE_CONFIG` (file), `OPENCODE_CONFIG_DIR` (extra plugins dir) and
  `OPENCODE_CONFIG_CONTENT` (inline JSON).
- Unverified for v2: the hook names and whether `OPENCODE_CONFIG*` is still honoured.

**A4 Unattended** (V, https://opencode.ai/docs/permissions/, https://opencode.ai/v2/docs/permissions):
- `--auto` auto-approves anything not explicitly denied. There is no yolo flag.
- v1 `permission`: `allow|ask|deny` per tool, with bash glob patterns where the last match wins;
  `OPENCODE_PERMISSION` holds inline JSON. v2 uses an ordered `{action, resource, effect}` list
  with the `shell` action, defaulting to ask.
- XDG paths: `~/.config/opencode`, `~/.local/share/opencode`, `~/.cache`, `~/.local/state`.
- Isolation (I, unverified): v1 `OPENCODE_CONFIG_DIR` adds config on top of global config, which
  still loads and merges (https://opencode.ai/docs/config/#custom-directory). Auth and storage
  isolation is therefore unproven. v2 offers `--standalone` or `service set disabled true`.
- First-run login (`opencode auth`) blocking a fresh pane is untested.

**A5 Queen** (V, https://opencode.ai/docs/rules/, /plugins/):
- Rules precedence: local AGENTS.md (wins over CLAUDE.md in the same dir), then global
  `~/.config/opencode/AGENTS.md`, then `~/.claude/CLAUDE.md` as a fallback. `instructions` adds
  files.
- Guard: a v1 plugin's `tool.execute.before` can throw to block. Without code, use
  `"permission": {"*":"deny","bash":{"*":"deny","hive *":"allow"}}` (I, from the documented
  last-match rule).
- v2 scans shell commands with tree-sitter into resources, and any deny wins, so `hive x | sh`
  should be denied (I, untested). v2 `policies` can only tighten.

**A6**: `curl -fsSL https://opencode.ai/v2/install | bash`, npm `@opencode/cli`, brew
`anomalyco/tap/opencode-v2`, AUR, Nix. Linux x64/arm64 glibc/musl. MIT.

## pi

Identity (V): the pi coding agent (binary `pi`, https://pi.dev). It started as Mario Zechner's
badlogic/pi-mono and is now https://github.com/earendil-works/pi, npm
`@earendil-works/pi-coding-agent` (formerly `@mariozechner/...`). Not installed locally or on
swarm (V).
Sources: https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/
pages `rpc.md`, `cli.md`, `sessions.md`, `extensions.md`, `security.md` and `configuration.md`.
They were read through a summarizing fetch, so the exact wording is at some risk.

- **A1** (V): `--mode rpc` is JSONL on stdin/stdout for a child process, with no network
  listener and no attach to a running TUI. There is an SDK and `RpcClient`. Community packages
  such as `pi-telegram-plus`, `@jenausmax/pi-telegram-extension` and `@r3b1s/tmux-pilot` exist
  (unverified). The closest option is tmux plus ssh.
- **A2** (V):
  - `-n/--name` sets the display name.
  - `--session-id <id>` opens or creates that id, the best fit for hive-assigned ids.
  - `--session <path|id>`, `-c`, `-r` (picker), `--fork`, `--no-session`.
  - `--session-dir` or `PI_CODING_AGENT_SESSION_DIR` moves the sessions. The default is
    `~/.pi/agent/sessions/`, per cwd.
- **A3** (V):
  - Extension events: `agent_start`, `agent_end`, `turn_end`, `tool_call`, `tool_result`,
    `session_start`/`shutdown`, `agent_settled`.
  - `agent_end` can be followed by retries or compaction. **`agent_settled` is the done
    signal.**
  - `-e/--extension <path>` loads an extension per process and is repeatable.
- **A4** (V): no tool permission prompts and no sandbox ("Pi does not ask before every tool
  call"). The project-trust prompt is settled with `--approve`/`--no-approve` and stored in
  `~/.pi/agent/trust.json`. `PI_CODING_AGENT_DIR` relocates auth, sessions and trust. Login is
  `/login` in-session. Whether provider env vars work is unverified.
- **A5** (V): it loads `AGENTS.override.md`, `AGENTS.md` and `CLAUDE.md` from the agent dir, cwd
  and parents. `SYSTEM.md`/`APPEND_SYSTEM.md` and `--append-system-prompt` add more. A
  `tool_call` handler returning `{block: true, reason}` blocks, and a throw also blocks, so this
  is the guard equivalent. `-t` is a tool allowlist. Extensions run with full OS rights.
- **A6** (V): `curl -fsSL https://pi.dev/install.sh | sh`, npm, Nix. MIT, version 1.4.0, Node
  >=22.19.
- Suggested launch (I, untested):
  `PI_CODING_AGENT_DIR=<dir> pi -n {name} --session-id {name} --approve -e <hive-hook.ts>`.

## B. tmux generic idle heuristics

Local tmux is 3.2a and swarm has 3.5a (V), so use only formats present in 3.2. Sources: local
`man tmux` and live read-only `list-panes`/`capture-pane`.

Seen live (V): Claude panes show `pane_current_command=claude`, `alternate_on=1` and the title
`✳ <session name>` (no busy/idle glyph change seen). `pane_last_activity` is empty on 3.2a. In
`capture-pane -p` hashes taken 5 s apart, the idle queen pane was stable and a working pane
changed, because of Claude's live "42s · ↓ 21.2k tokens" counters.

| Signal | Supports | Failure modes |
|---|---|---|
| `pane_current_command` is a shell | "agent exited, prompt returned" | Constant while the agent lives. Wrappers and `exec` change it, and node/bun children can show transiently. |
| `pane_dead`/`pane_dead_status` | exit plus exit code | Needs `remain-on-exit`, and only on exit. |
| `pane_pid` + `/proc` tree | foreground process | Tool subprocesses (bash, MCP) flicker. |
| `window_activity` (now − t) | "quiet N s" | Per window, not per pane. Spinners and counters count as activity. Only works for one pane per window. |
| `monitor-silence N`, `window_silence_flag`, `alert-silence` hook | tmux-side timer | Needs `set-option`/`set-hook` (mutation). The flag clears when viewed. Redraw defeats it. |
| `pipe-pane -o` + timestamps | exact last-output time | One pipe per pane, it is a mutation, every redraw counts, and it needs a reader. |
| `capture-pane -p` hash stable N s | idle for Claude-like TUIs | A blocked permission dialog is also stable, so stable means "idle or blocked". Clocks or animated idle screens never settle. Alternate screen means visible screen only. |
| `cursor_x/y`, `pane_title` | weak hints | Layout-dependent. The title is per agent and may be static. |

I: no tmux signal tells "done" from "waiting for approval". Use the agent-native events from A3
as primary, and keep the hash plus liveness check as a generic fallback with a status of
`busy|quiet|dead`, not `done`.

  `.zshenv` for every invocation (V). On a bash host this would fail: a non-interactive bash
  returns early from `.bashrc` (I, standard Debian `.bashrc`). Robust form: call
  `$HOME/.local/bin/hive` (V, works on swarm), or make the remote command path configurable per
  node.
- An unreachable host exits 255 (V, `nosuchhost.invalid`). Otherwise ssh passes the remote exit
  code through (man ssh). hive's own codes (for example `status` exits 1 when not running, and
  `spawn` exits 3 when untrusted) therefore survive. Treat 255 as a transport error.
- Command shape (I, from man pages):
  `["ssh", "-o", "BatchMode=yes", "-o", "ConnectTimeout=5", host, shlex.join(["hive", *args])]`.
  The remote shell re-parses the string, so `shlex.join` is required.
- `hive attach` needs a tty: `ssh -t`, or `-tt` when local stdin is not a tty (man ssh). Not
  run.
- The queen guard forbids pipes and chaining, so a remote call must be a hive subcommand (for
  example `hive --node swarm list`), not `ssh swarm hive list` typed by the queen (I).
- hive output is line records, not JSON. A remote queen parsing `list`/`status` text across
  versions is brittle (I). Version skew is visible through `hive --version`.

## Implications for the driver abstraction

These are fields a driver needs, drawn from the findings above. They are not a design.

1. `name`, `binary` and a launch template with placeholders `{name}`, `{session_id}`, `{dir}`.
   Only Claude and pi take a launch-time name. Codex needs a post-launch `/rename`, and OpenCode
   needs an API PATCH or nothing.
2. `remote`: one of `per-session` (Claude `--remote-control {name}`), `server`
   (OpenCode serve/web/pair, Codex app-server, experimental), or `none` (pi). hive's current check
   "command must contain --remote-control" becomes per-driver.
3. `remote_requirements`: Claude needs subscription auth. OpenCode needs a server password and
   port. Codex is experimental and its Linux pairing is unverified.
4. `session_id_mode`: `assign` (Claude `--session-id <uuid>`, pi `--session-id`) or `discover`
   (Codex from the SessionStart hook or rollout, OpenCode from the API). Plus the `resume` argv
   for an id or name, and the arguments that must be passed again on resume (Claude
   `--settings`).
5. `done_signal`: the hook injection method and event names (table row A3), with a tmux hash
   fallback. A shared per-pane status file (`busy|done|blocked|dead`, `session_id`, timestamp)
   keeps the queen agent-agnostic.
6. `unattended_args` (`--permission-mode auto`, `-a never -s workspace-write`, `--auto`, none)
   plus a per-driver trust pre-seed (table row A4), and `known_blocking_dialogs` for `waiting=`
   detection.
7. `config_dir_env`: `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `OPENCODE_CONFIG_DIR` (v1) /
   XDG plus `--standalone` (v2), and `PI_CODING_AGENT_DIR`. The trust-file logic moves behind the
   driver, which preserves hive's rule that the launcher, not hive, sets the env.
8. Queen support:
   - `instructions_file`: CLAUDE.md, AGENTS.md (Codex, OpenCode, pi).
   - `guard_mechanism`: Claude PreToolUse allow/deny/ask; Codex PreToolUse deny-only;
     OpenCode a plugin throw or permission patterns; pi a `tool_call` block.
   - `supports_ask`: false for Codex. For pi, only via `ctx.ui.confirm` inside `tool_call`
     (unverified). Unverified for OpenCode. The guard's "ask" paths need a fallback.
9. `node`: `host`, `hive_path` (default `$HOME/.local/bin/hive`), `ssh_opts`, and whether the
   node runs a queen. The ssh exit code 255 maps to an unreachable node.

## Risks, open questions, gaps

- Decision needed: OpenCode v1 or v2. The config, permission and plugin APIs differ.
- Untested everywhere: a first launch in a fresh config dir (onboarding, RC consent), Claude
  `--resume` plus `--remote-control` reattach behaviour, Codex `-c` hook injection and hook trust,
  an OpenCode TUI and browser on one session, and the pi `-e` extension in a tmux pane.
- Claude `auto` pauses after 3 consecutive or 20 total classifier blocks, so a long-running
  worker can stall silently. The `Notification` hook should catch it, but this is unverified.
- Incident: during research, the OpenCode worker printed `~/.config/opencode/service.json`. That
  exposed the local OpenCode service password in a subagent transcript. Rotate it
  (`opencode service set ...` or delete and recreate).
